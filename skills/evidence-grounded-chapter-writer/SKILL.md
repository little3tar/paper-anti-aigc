# Evidence Grounded Chapter Writer

## Red Flags（停止并检查）

| AI的想法 | 正确做法 |
|---|---|
| "这个参数看起来合理，写进去" | 参数必须有来源或标为 `[设计假设: ...]` |
| "公式推导差几步，我补全" | 不补写用户未提供的计算步骤和中间结果 |
| "这段缺文献，编一个看起来真的" | 缺文献写入证据缺口，不伪造 |
| "图表占位符放章尾清单就行" | 占位符必须放在正文第一次引用位置 |
| "标准规范写个标准号就够了" | 已核验标准需写明名称、标准号、版本/年份、适用范围 |
| "标准就是文献，用 `[煤矿安全规程]` 格式引用" | 标准/规程/规范必须用 `[标准规范: ...]` 工作标记，禁止使用 `[文献题名]` 格式。两类标记处理路径不同——详见 `citation-key-rules.md` §标记格式选择 |
| "用户说'写第X章'、沉默、或预授权模式下，AI 倾向跳过确认直接写正文" | 细纲必须经用户显式确认后才能进入正文写作。预授权只跳过文件生成/格式询问，不跳过内容确认。沉默不等于同意 |
| "标题下面写一句简介就可以进下一节了" | 节标题（如 §2.2）后至少展开一段充分论述再进入小节（§2.2.1），禁止单句孤悬段落后直接跳下一级标题 |
| "用户给了参数，直接写成产品规格" | 用户提供的参数需先判断是 A 类（产品公开规格）、B 类（用户设计选择）还是 C 类（待推导），分类不明时必须询问，不可默认写成产品定论 |
| "Zotero 有笔记，直接读了用" | 检测到 Zotero 笔记/标注时必须先征求用户同意再读取，不可自动使用 |
| "写完初稿，直接写入主文件" | 初稿写入 `.thesis-workflow/chapters/chX/draft.md`，主文件只在全部五阶段完成、用户显式确认后才修改 |
| "证据表有 12 篇文献，一次性拉全部笔记" | 按节分批获取，每批 2-3 篇，先写入缓存文件再逐节写作。标记为 `无笔记` 的文献不重试，不卡在获取步骤循环 |
| "这篇文献笔记获取失败，再试几次" / "这里缺个数据，Zotero 没找到就算了" | 笔记获取每篇最多 1 次，失败后标记状态并继续；缺来源时必须三级全部尝试（见 workflow 参考文件 `source-policy.md`），不得在任一级提前放弃 |
| "这个参数用经验公式估算一下就行" | 必须先尝试补齐输入参数（Zotero → 用户 → 网络三级检索），确实无法获取时才标 `[设计假设: ...]`。不得跳过完整推导链直接给估算值（规则见 workflow §来源策略） |
| "用户确认过的参数，写作时再说" / "证据表列了文献，直接写正文就行，笔记缓存可以跳过" | 用户在任何阶段确认/补充的信息必须在回复后立即写入对应 ledger 文件（见 workflow §用户确认/补充信息的落盘规则）。步骤 3 必须按分批获取协议获取当前节文献笔记并写入 `.thesis-workflow/chapters/chX/literature-notes.md`；步骤 4 每节写作前检查缓存，未缓存的笔记补获取后追加写入。不得跳过缓存直接基于题名/摘要写作 |
| "图表占位符写了就行，代码后面再说" | 简单流程图/架构图/算法框图在输出"图片与表格占位符清单"时，必须同时附加 Mermaid 代码块、matplotlib 脚本或 Graphviz DOT 文件作为可渲染附件，复杂示意图附提示词模板。不得只留 `[此处插入图片：...]` 空占位符 |
| "图表台账 manifest 好像有个文件，不用管" | 章节写作完成后必须更新 `.thesis-workflow/figure-data-manifest.md`，逐图填充 Figure ID、数据文件、来源说明、生成脚本、输出格式和状态。规则见 `references/figure-data-manifest-rules.md` |
| "这章写完了，更新 outline.md 的进度/事实/缺口" | outline.md 规划阶段后冻结。进度 → `ledger/chapter-status.md`；事实 → `ledger/facts.md`；图表 → `figure-data-manifest.md`。不修改 outline.md。 |

在 thesis outline 或章节目标已经明确后调用。写出有证据边界的章节草稿——杜绝为了让正文完整而编造事实、参数、公式或文献。

## 工作流程

1. **确认写作目标**
   - 确认章节编号、节范围、预期字数、引用样式和输出格式。
   - 文件产出规则遵循 workflow §输出与文件安全。本阶段产物为 `.thesis-workflow/chapters/chX/draft.md`。初稿不直接写入主文件。
   - 只有当格式会影响工作时才问输出格式。
   - 如果存在 project ledger（`ledger/` 目录），先读取 `ledger/facts.md` 和 `ledger/decisions.md`。
	   - 读取 `.thesis-workflow/literature-pool.md`（如存在），获取上游大纲规划阶段建立的文献池全表及 ZoteroKey 映射，避免重复检索已有文献。
	   - 读取 `.thesis-workflow/materials-inventory.md`（如存在），获取用户已编目的材料清单及其数据性质分类（A/B/C），后续写作中直接引用已分类参数。
	   - 读取 `.thesis-workflow/main-tex-context.md`（如存在），获取项目特定格式约定：标题格式、中英双语规范、图表命名规则、引用方案和排版约定。写作全程遵循其中的格式要求。

2. **生成章节细纲并等待确认（强制门控）**
   - 把章节拆成节、小节和段落级写作点。
   - 标出每个写作点需要的文献、公式、设计假设、图、表或用户数据。
   - 涉及建模、计算、选型、实验、仿真、算法或定量比较时，标出预期的公式/参数工作。
   - 不要在用户主题和证据尚未要求时强行加入领域公式。
   - **细纲必须经用户显式确认后才能进入步骤 3（检索和整理证据）和步骤 4（撰写正文）。** 确认后的细纲写入 `.thesis-workflow/chapters/chX/detailed-outline.md`，大纲文件 `outline.md` 只保留到小节标题层级。
   - 用户回复"确认""可以""继续""没问题"或对细纲内容提出具体修改意见，才算确认。用户只说"写论文""写第X章"等未涉及细纲内容的表述，不算确认。
   - 仅当用户在请求中已包含**经用户本人编写**的完整细纲（非 AI 生成），才可跳过此确认步。
   - **用户补充/确认的信息立即落盘（⭐ 全流程适用）**：用户在任何阶段确认或补充的信息，必须在回复后立即写入对应 ledger 文件。完整规则（落盘目标映射表等）见 workflow §用户确认/补充信息的落盘规则。

3. **检索和整理证据**
   - **三级信息源强制 fallback（⭐）**：每个待检索的证据/参数/文献，遵循 workflow §来源策略中的强制三级检索协议（Zotero → 用户 → 网络），每项都要尝试。只有三项都尝试过仍未获取的，才能列入 `证据缺口清单`。
   - 章节涉及行业标准、国家标准、规范、规程、验收要求或限值时，同样按三级 fallback 检索：先查 Zotero/本地文献，不足时询问用户是否有标准文件，最后搜索官方标准平台、主管部门、标准发布机构、出版社页面或其他可靠来源。
   - **建立证据表**：起草前为本章建立小型证据表，列出每篇文献的题名、作者/年份、来源类型、可支撑的论点、对应的细纲段落。在证据表中标注每篇文献映射到哪些节/小节。
   - **文献笔记分批获取（⭐）**：遵循 `references/literature-notes-cache-rules.md`。不要在证据检索阶段一次性拉取所有文献的笔记。
     - **首次获取前询问用户授权**：
       > "检测到以下文献在 Zotero 中有笔记/标注：[首批 2-3 篇文献题名]。是否允许我分批参考笔记内容？笔记将缓存到 `.thesis-workflow/chapters/chX/literature-notes.md`，按节分批获取。"
     - 用户同意 → 创建 `.thesis-workflow/chapters/chX/literature-notes.md`（如不存在），首批获取第一节直接引用的 2-3 篇核心文献笔记，写入缓存
     - 用户不同意 → 本章全程不使用笔记，仅使用题名/摘要等公开元数据
     - 每篇文献最多尝试从 Zotero 获取笔记 1 次。获取失败或确认无笔记后标记 `无笔记` 或 `获取失败`，不重试 Zotero 笔记获取。笔记获取失败≠证据检索结束——文献的完整信息（标准号、版本/年份、参数值等）仍须通过三级检索协议的用户→网络步骤补全，不卡在获取步骤
     - 后续批次在每节写作前获取（见步骤 4）
     - 笔记内容是用户个人理解，用作写作参考，**不替代对文献原文的核实**
   - 已核验的标准规范应作为正式支撑来源写入证据表，标明标准名称、标准号、版本/年份、发布机构和适用条款或范围。
   - **文献池不足时主动补搜**：如果检索后发现可用文献数量不达标（完整章 10+ 篇，小节 3+ 篇），或关键论点无人支撑，不要静默进入写作。应主动扩大检索范围（Zotero 全文检索、Web 补充检索），并将新发现的文献纳入证据表。确实无法补全的主题在细纲和证据表中标注后继续，但正文中不得用模糊归因掩盖缺口。

4. **撰写章节正文（逐节推进 + 分批获取笔记）**
   - 按细纲中的节顺序逐节写作，不要一次性生成全章。
   - **产物管理**：逐节写作的中间文本写入 `draft.md`（逐节追加，全章完成后形成完整草稿）。不在对话框中逐节展示全文请求确认——步骤 2 的细纲确认门控是正文写作前唯一的用户确认点。节间仅做内部检查（读取下节缓存、获取下批笔记、更新"已用于段落"），不设用户确认停顿。
   - **每节写作前**：
     1. 检查 `.thesis-workflow/chapters/chX/literature-notes.md` 缓存，读取当前节相关文献的笔记条目（仅读取状态为 `已获取` 的条目；`无笔记` 和 `获取失败` 条目跳过）。
     2. 如当前节需要的文献笔记尚未缓存且状态非 `无笔记`/`获取失败`，获取该批（1-3 篇）文献笔记，追加写入缓存。
     3. 从标注内容中提取支撑当前段落的关键发现；从笔记内容获取用户理解角度。
   - **每节写作完成后**：更新缓存中该文献条目的"已用于段落"。
   - 不要提前把整章所有文献笔记加载到上下文。只读取当前节相关的条目。
   - 使用中文工程论文风格。
   - **段落结构规则**：节标题（如 `§2.2`）之后，禁止仅用一句简介就直接跳入下一级小节标题（如 `§2.2.1`）。每节在引入小节之前，必须先展开至少一段充分论述——说明本节要解决什么问题、涉及的工程对象或方法背景、与上下节的逻辑关系。小节标题之间同样要求：两个小节标题不能相邻（中间必须夹正文段落）。如果某节内容确实不足以展开，应合并到相邻节中，而不是保留一个空壳节。
   - 在需要正式引用的位置插入 `[参考文献]`。
   - 在被支撑论点附近或证据表中保留 title-based source marker，方便后续 bibliography 解析。
   - 将 `[此处插入图片：...]` 和 `[此处插入表格：...]` 放在正文第一次需要出现图表的位置；尾部清单只能汇总，不能替代正文插入点。
   - 对于占位符中的简单流程图、架构图、算法框图，在输出"图片与表格占位符清单"时附加对应的 Mermaid 代码块或 Python matplotlib 脚本作为可渲染附件，不要仅留空白占位符。复杂示意图（需自由绘制）使用提示词模板。
   - 公式统一用 LaTeX math，便于在 Markdown、LaTeX 和 Word/MathType 流程之间迁移。
   - 工程计算段按 `formula-calculation-rules.md` 定义的 8 步计算链（设计目标→公式与来源→符号定义→参数表与来源类型→代入数值→结果→单位检查→工程裕量/选型结论）展开，**任一环节缺失时不得给出计算结果**。缺失环节必须通过三级信息源（Zotero → 用户 → 网络）补齐，或标为 `[设计假设: ...]`。计算链先写入 `.thesis-workflow/calculation-records.md`（完整底稿），再选取关键步骤写入正文段落（计算叙述）。规则见本 skill 参考文件 `calculation-records-rules.md` 和 `formula-calculation-rules.md`。
   - **发现计算缺口时主动补充（⭐）**：编写工程计算段落时，若发现正文需要某个计算类数值（如缸径、推力、功率）但 `calculation-records.md` 中无对应记录，**必须先补充完整计算记录**（公式→符号表→参数来源→代入→结果→单位检查→标准选型），再选取关键步骤写入正文。不得绕过计算记录直接给估算值或跳过推导。
   - 缺少证据或参数时，不把 unsupported fact、parameter、formula 或 conclusion 写入正文；记录到 `未写入正文的待补资料`、`证据缺口清单` 或 project ledger。
   - 后续章节需要用户自制材料时，直接列入 `待用户补充的信息`，例如图纸、结构尺寸、实验记录、仿真截图、程序输出、设备选型依据、现场照片或导师批注；不要用常识替用户补造。
   - 用户已提供且确认的参数，按四级消化规则处理：优先找外部来源；找不到则尝试公式推导；无法推导则用工程语言解释选取依据；最后手段才是 `[设计假设: 基于 Mxx]`。正文中不得出现 `[用户材料: ...]` 或 `[Mxx]` 标记。
   - **A/B/C 分类表述规则**（⭐）：用户提供的参数在写作前必须明确分类，按类别选择表述语气。参数分类和表述语气的完整定义见 workflow §用户材料收录协议。核心禁忌：B 类用户设计选择禁止用 A 类语气写成"MC51 采用/配备/配置了..."的产品定论。
   - 已核验的标准规范应融入正文表达，用于支撑设计参数、限值、选型依据、验收要求或安全裕量。正文中写明标准名称、标准号、版本/年份和适用范围，并保留 `[参考文献]` 或最终模板要求的引用格式。
   - 未核验的标准规范只保留在 `证据缺口清单` 或工作稿 source note 中，不写成正文定论。
   - 区分 `影响关系` 和 `可计算公式`：概念关系式可说明变量影响方向；可计算公式必须有来源、符号定义、参数值、代入、单位检查和结果。
   - 用户确认的假设只有在明确标为 `[设计假设: ...]` 时才进入正文。
   - 新确认的事实、参数、公式或设计决策，应写入或准备写入 project ledger，而不是只留在聊天记录里；未经用户确认的内容只能作为 draft、needs-source 或 needs-user-data 记录。

5. **完成章节交接**
   - 更新 `.thesis-workflow/figure-data-manifest.md`：逐图填充 Figure ID、数据文件、来源说明、生成脚本（Mermaid/matplotlib/DOT 代码块或提示词模板）、输出格式和状态。规则见 `references/figure-data-manifest-rules.md`。
   - 提供来源清单、未支撑项、需要用户补充的数据和推荐下一步。
   - 推荐先运行 `reference-integrity-auditor`，再进入 `engineering-paper-humanizer` 和 `academic-format-cleaner`。

## Source Marker 规则

生成 reference placeholders 或来源表时读取 `references/citation-key-rules.md`。

章节涉及公式、参数、建模、推导、计算、设计选型、实验/仿真数据、算法或定量比较时读取 `references/formula-calculation-rules.md`。

使用或更新已确认项目事实、公式、来源和设计决策时读取 `references/project-ledger-rules.md`。

工作稿 source marker 格式遵循 `references/citation-key-rules.md` 统一定义。

题名规则：

- 中文文献使用原中文题名。
- 英文文献使用原英文题名，不要强行小写、去空格或改写。
- 如果题名重复，在 marker 内追加作者和年份，例如 `[A development in rock cutting technology Hood 2000]`。

## 输出模板

完整章节草稿默认返回（标注"主文件"的项进入最终输出，其余仅工作稿）：

1. `章节细纲`（工作稿）
2. `证据表`（工作稿）
3. `公式与参数计划`（工作稿）
4. `正文初稿`（→ **主文件**：含章节标题、段落、图表占位符）
5. `图片与表格占位符清单`（→ **主文件**：Mermaid/代码块/提示词模板嵌入正文对应位置，图名表名含中英双语）
6. `参考来源清单`（工作稿）
7. `待用户补充的信息`（工作稿）
8. `未写入正文的待补资料`（工作稿）
9. `证据缺口清单`（工作稿）
10. `后处理建议`（工作稿）

如果用户已经批准直接起草，可以省略确认停顿，但仍必须把 unsupported items 放在缺口区，而不是写进正文。

## 缺参数章节模板

当章节需要计算但任务书缺少参数时，使用这个结构：

1. 说明设计目的和当前数据边界。
2. 提供参数来源表，列为 `参数`、`含义`、`来源状态`、`备注`。
3. 不可用数值不进入正文，列入 `未写入正文的待补资料`。
4. 只有用户明确确认后才使用 `[设计假设: ...]`。
5. 概念性内容放在 `影响关系`；可计算内容放在 `可计算公式`。
6. 每个可计算公式都包含来源、符号、代入、结果、单位检查和裕量；缺任一项时，只作为公式计划，不写计算结论。
