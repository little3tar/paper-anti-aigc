# Engineering Paper Humanizer

深度重写工程类学术文本，减少模板化、机械化和聊天式表达。在保留原意、专业术语、文献引用和 LaTeX 命令完整的前提下，使其呈现出人类工程师真实、严谨且带有“工程粗糙感”和长短句顿挫的行文风格。不仅要“干净”（无冗余套话），更要“鲜活”（有真实人味）。

## Core Principle

1. **保留原意** — 术语替换会导致学术语义偏移，引用丢失会破坏论证链条。专业术语、`\cite{}`、LaTeX 命令保持原样不动。
2. **减少机械腔** — 按核心维度逐条扫描降解（详见 `references/rewrite-guide.md`）。
3. **注入人味与灵魂** — 避免无菌、没有声音的机器感写作。引入工程妥协语态、定量参数碾压、长短句顿挫极化。
4. **禁止捏造数据** — 编造数字是学术不端硬伤，一旦被查无法辩护。只用原文已有数据或可追溯推导。
5. **严格文献引用真实性** — ⛔ **绝对禁止编造文献引用**。若改写需添加 `\cite{}` 引用，必须获取真实文献内容并确保与前后文相关。无真实文献依据时，删除模糊归因改用客观陈述（详见 rewrite-guide.md 规则 L3a）。
6. **标点硬约束** — 中文正文禁用 ASCII 直双引号 `"..."`，改用中文弯双引号 `“...”`；嵌套引用用 `‘...’`；书名、论文名、标准名优先用 `《...》`；代码、命令、变量、文件名用反引号或 LaTeX 等宽命令，不用引号。除数学区间、复合词、页码范围等必要场景外，删除破折号，改用逗号、分号、句号或“即”“也就是说”等自然连接。

## Step-by-Step Process

### Phase 1：准备阶段（Git 备份 + 背景知识预检）

1. **安全备份**：在对任何文件进行修改前，执行 Git 分支备份。若当前目录非 Git 仓库，自动初始化 Git 后创建备份分支；若 Git 未安装或初始化失败，则执行文件复制备份：

   ```bash
   python <SKILL_DIR>/scripts/git_snapshot.py <TARGET_FILE>
   ```

   脚本执行逻辑：
   1. **Git 备份（首选）**：若当前目录是 Git 仓库，创建分支备份；若非 Git 仓库，自动尝试 `git init` 初始化
   2. **文件备份（回退）**：若 Git 未安装或初始化失败，则在 `.humanizer-backups/` 目录下执行文件复制备份
   3. **去重检测**：对比文件内容哈希，避免重复备份相同内容

2. **背景预检**：快速扫描 `main.tex` 章节结构与核心参数，与 `references/main-tex-context.md` 交叉比对。若发现显著偏差，警告用户并建议按模板更新。用户拒绝则使用现有版本继续。

### Phase 2：扫描解构

读入用户草稿，按 `references/rewrite-guide.md` 逐段定位 AIGC 痕迹：

- 五大核心规则分类逐条扫描
- 个性与灵魂指南识别“缺乏灵魂的写作迹象”
- 运行 `check_aigc.py` 标记敏感词组和格式问题

### Phase 3：重构注入（重写 + 格式修复 + 自检）

1. **执行重写**：结合宿主文档背景事实，按核心维度执行重写。严格遵守**数据完整性红线**（见下方表格）和 **LaTeX 绝对保护红线**（见 `references/rewrite-guide.md` Part 3）。
2. **格式修复**：运行自动检查脚本，根据输出的精确行号逐条修复：

   ```bash
   # LaTeX 文件（默认）
   python <SKILL_DIR>/scripts/check_aigc.py <TARGET_FILE>

   # Markdown 文件
   python <SKILL_DIR>/scripts/check_aigc.py <TARGET_FILE> --format markdown

   # 纯文本文件
   python <SKILL_DIR>/scripts/check_aigc.py <TARGET_FILE> --format plain
   ```

   修复完毕后再次运行脚本确认 error 清零。

3. **自检**：`check_aigc.py` 输出即为自检结果。此外，对照以下脚本无法覆盖的结构性问题速查表：
   - ✓ 连续 3 句以上长度相近？→ 打断其中一句，制造长短句顿挫
   - ✓ 段落以简洁单行“金句”结尾？→ 改为技术细节或直接删除
   - ✓ 任何地方有三项顺序并列？→ 改为两项或四项，打破三段式模板
   - ✓ 有比喻/类比后紧跟解释？→ 删除解释，信任读者能理解
   - ✓ 全段只有陈述没有数字？→ 补充定量参数（百分比、单位值）
   - ✓ 段落读起来像产品新闻稿或维基百科？→ 注入工程妥协感和真实困境
   - ✓ 有破折号“——”或 em dash `—`？→ **删除改用逗号、分号、句号或明确连接词，确保前后衔接自然**（详见规则 E8）
   - ✓ 有 ASCII 直双引号 `"..."`？→ **按语境改为 `“...”`、`‘...’`、`《...》`、反引号或直接删除强调引号**（详见规则 F2）

### Phase 4：输出交付

输出重写后的代码块（LaTeX/Markdown/纯文本），并附加所做更改的简要总结（可选但推荐）：

````markdown
**改写后的文本：**

```latex
[重写后的内容]
```

**主要更改说明：**

- 删除了“...” （原因）
- 将“...”改为“...” （原因）
- ...
````

**更改说明示例：**

> - 删除了“为了解决...问题”（填充短语）
> - 将“此外，实验表明”改为“测试数据”（删除 AI 高频连接词）
> - 将破折号“——”改为逗号（避免破折号滥用）
> - 补充了“超调量从 12.3% 压至 4.7%”（定量参数替代“显著提升”）

### Phase 5：后续维护（可选）

1. **质量评分**：若用户要求评估机械化程度、模板化程度或改写质量，按 **references/optional-checks.md** 中的质量评分标准（五维评分）执行评估。
2. **背景知识同步**：完成所有修改后，询问用户是否需要同步更新 `references/main-tex-context.md`。若确认，则读取最新 `main.tex` 全文并按模板覆盖写入。

## Data Integrity Red Line

| 优先级  | 数据来源 | 规则                                                    |
| ------- | -------- | ------------------------------------------------------- |
| P1 首选 | 原位数据 | 直接复用宿主文档或用户提供信息中的真实数据              |
| P2 次选 | 推导论证 | 基于已有参数做物理/数学推算，必须展现推导链条与计算过程 |
| P3 末选 | 外部检索 | 极少数情况，必须标注信息源（“根据 XX 手册”）            |
| ⛔ 禁止 | 凭空捏造 | 编造数据属学术不端，不得臆造文档中未提及的数字或结论    |
